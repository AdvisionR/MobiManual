LDAP Settings

  • Config >> Ldap Settings, opens the interface which supports the logged in user to set ldap settings

  • LDAP settings are configured in this page.

  • LDAP settings are managed in different sections. These sections are, “Connection Settings, Search Settings, Authentication Settings, Field Mappings” . You can navigate between these tabs by either clicking related tab or clicking continue button right of the bottom of the form

  • Connection Settings: To perform any operation in ldap directory , firstly you should bind with correct url ,admin name and admin password. “LDAP Url, Admin Domain Name and Admin Password” is entered into related fields.

  • Search Settings: These settings are used to search a user . In detail :

    • “Search Base” determines from where to begin to search item in directory hierarchy.

    • “Search Filter” as understood from its name , is used for filtering searches.

    • “Search Scope” decides search behaviour .

      • base - For searching only the base entry.
      • one - For searching only the children of the base entry.
      • sub - For searching the base entry and all its descendants.

    • You can choose attributes you want to return from search operation by writing names of them to Attributes to return field separating with comma . Do not put space anywhere

  • Authentication Settings: This section is related to authentication of the ldap user .

  • “CN (Common Name)” or “DN (Domain Name)” is selected from list according to the type of the active directory. For example , while a user is authenticated by dn in OpenLDAP , cn is used for authentication in Microsoft Active Directory . If your ldap directory type is OpenLdap ,select “DN” then a new field “Search Filter” will be visible.Since you will send only username and password information , dn should be found to authenticate especially when enrolling device to the your system.This is why you should set the search filter .In case of Microsoft Active Directory , there is no need for search filter because it authenticates by cn directly.

  • If the usernames in your system and cns in ldap directory are different but related in some patterns , you can supply the parts for replacement. It can be , for example, the user names are like email addresses i.e @.com , however CNs are simply in your ldap directory Then, you can set replace field as “@.com” and with field as “” .

  • Field Mappings:

You can add ldap users to your system from ldap tab of the add user page by searching ldap user and simply click save button.Which fields in ldap correspond to which fields in your system is determined in Field Mappings tab . To illustrate , if you choose “mail” for “UserName Fields” , you should sign in with ldap mail in your system because your username field matches with mail of the ldap directory item.Similarly , you can set fields (putting commas between them) to construct display name.

From any tab you can save whole settings by clicking save button , and also you can test your settings for each tab .

Web Action Logs / Audit Logs

Web Action Logs are used to audit actions performed in the MDM admin panel. This page helps administrators understand who did what, when it was done, from which IP address, and which system function was affected.

Users » Audit opens the Web Action Logs page.

Using Web Action Logs

The admin can filter audit records by:

  • User to see actions performed by a specific admin.
  • Action to filter request types such as create, update, delete, or test actions.
  • URL to find which admin panel function or backend endpoint was used.
  • IP Address to identify where the action came from.
  • Start Date and End Date to review actions in a specific time period.
  • Advanced Search to search inside detailed log data.

Understanding Log Records

Each log record shows the action details in a structured way:

  • IP shows the source address of the admin request.
  • User Name shows which admin account performed the action.
  • URL shows the system endpoint that was called. This usually represents the feature that was used, not a website visited by a device.
  • Action shows the request method, such as POST, GET, PUT, or DELETE.
  • Date shows when the action happened.
  • Data shows the submitted values or request details, usually in JSON format.

The Data field is useful when the admin needs to understand exactly what was changed or sent. For example, it may show policy values, VPN configuration details, selected apps, device commands, or other configuration data submitted from the admin panel.

Call Blacklists

Call Blacklists are used to block outgoing calls to selected phone numbers or number patterns. A blacklist rule is created with a regular expression and then applied to devices through policies.

Policies » Call Blacklists opens the Call Blacklists page.

Add Call Blacklist

In the Add New area, enter the number rule into the Enter A Regular Expression field.

The rule can target a single number, multiple numbers, a number prefix or a wider number pattern. The rule should be written according to the number format used on the device.

Test

User can test if their REGEX match with desired output by editing the rule given.

Common examples:

  • .*
    Blocks all outgoing calls.
  • ^0900.*
    Blocks all numbers starting with 0900.
  • ^\+49.*
    Blocks all numbers starting with the country code +49.
  • ^(0530000000)$
    Blocks only the exact number 0530000000.
  • ^(0530000000|0540000000)$
    Blocks only the numbers 0530000000 and 0540000000.
  • ^05[0-9].*
    Blocks numbers starting with 05 followed by any digit.
  • ^[0-9]{4}$
    Blocks four-digit short numbers.

For exact number blocking, use ^ at the beginning and $ at the end of the rule. For prefix-based blocking, use .* after the prefix.

After the regular expression is entered, click Save to create the call blacklist. After the blacklist is saved, it must be added to a policy and assigned to the required users or devices.

Policies » Keyguard Features opens the Keyguard Features configuration page.

Configure Keyguard Features

Enter a Name for the configuration and optionally add a Description.

In the Android Features section, enable the restrictions that should be applied on the device lock screen.

The following options can be configured:

  • Disable All Features disables all available keyguard customizations in this configuration.
  • Disable Biometric Authentication disables biometric unlock methods on the secure lock screen.
  • Disable Face Authentication disables face authentication on the secure lock screen.
  • Disable Fingerprint Usage disables fingerprint unlock on the secure lock screen.
  • Disable Iris Authentication disables iris authentication on the secure lock screen.
  • Disable Quick Reply disables text reply actions from lock screen notifications, where supported.
  • Disable Camera disables camera access from the secure lock screen.
  • Disable Secure Notifications prevents notifications from being shown on the secure lock screen.
  • Disable Trust Agents disables trust-agent based unlock methods, such as trusted device or trusted location unlock.
  • Disable Unredacted Notifications allows only redacted notification content on the secure lock screen.

After selecting the required restrictions, click Save to create the configuration.

Permission Grant States

Permission Grant States are used to control Android application permissions from MobiVisor without requiring the user to approve them manually on the device.

This feature is available only for Android devices enrolled with Device Owner profile.

Policies » Permission Grant States opens the Permission Grant States page.

Permission Grant Concept

Normally, Android applications ask the user for permissions such as camera, location, phone or storage access. With Permission Grant States, the administrator can define how a specific permission should behave for a specific application.

A permission can be configured in three ways:

  • Auto Grant: The permission is allowed automatically.
  • Auto Deny: The permission is denied automatically.
  • Prompt User: The device asks the user to decide.

This is useful when company applications require certain permissions to work correctly, or when specific permissions should be blocked for security reasons.

Configure Permission Grant State

To create a permission grant state:

  • Enter a clear Name for the configuration.
  • Enter the application package name in the Package Name field.
  • Enter the Android permission value in the Permission field. The permission name should be obtained from the “Android Developers Develop API reference Manifest.permission” page.
  • Select the required value from Grant State.
  • Click Save.

The permission value should start with android.permission..

Examples:

  • To allow camera permission automatically:
    Package Name: com.example.app
    Permission: android.permission.CAMERA
    Grant State: Auto Grant

  • To block camera permission automatically:
    Package Name: com.example.app
    Permission: android.permission.CAMERA
    Grant State: Auto Deny

  • To let the user decide for phone permission:
    Package Name: com.example.app
    Permission: android.permission.CALL_PHONE
    Grant State: Prompt User

Saved permission grant states are listed at the bottom of the page. Existing configurations can be copied with Clone, updated with Edit or removed with Delete.

Sending Permission Grant States to Devices

Creating a permission grant state does not apply it to devices automatically. After saving the configuration, it must be added to a policy and assigned to the required devices or users.

To apply the configuration:

  • Create or edit the required policy.
  • Select the saved Permission Grant State in the policy.
  • Assign the policy to the target users or devices.

System Update Policies

System Update Policies are used to control when Android system updates are installed on managed devices. This feature is available only for Android devices enrolled with Device Owner profile.

Policies » System Update Policies opens the System Update Policies page.

Configure System Update Policy

Enter a Name for the policy and select one of the available update types.

The available update types are:

  • Automatic Update

    Installs system updates (without user interaction) as soon as they become available. Setting this policy type immediately installs any updates postponed or waiting. The user cannot install updates manually if this policy is applied. In order for the update to be fetched and installed, the device needs to be active and cannot be in sleep mode. Note: Whether an update is applied is dependent on Android.

  • Scheduled Update

    Installs system updates (without user interaction) during a daily maintenance window. Set the start and end of the daily maintenance window. The user cannot install updates manually if this policy is applied. In order for the update to be fetched and installed, the device needs to be active and cannot be in sleep mode. No connectivity, not enough disk space, or a low battery are typical reasons Android might not install a system update in the daily maintenance window. After 30 days trying to install an update in the maintenance window (regardless of policy changes in this period), the system prompts the device user to install the update. Note: Whether an update is applied is dependent on Android.

  • Postponed Update

    Postpones the installation of system updates for 30 days. After the 30-day period has ended, the system prompts the device user to install the update. The system limits each update to one 30-day postponement. The period begins when the system first postpones the update and setting a new postphone policy won’t extend the period. If, after 30 days the update isn’t installed (through policy changes), the system prompts the user to install the update.

After selecting the update type, click Save to create the system update policy.

Sending System Update Policies to Devices

Creating a System Update Policy does not apply it to devices automatically. After saving it, the policy must be assigned to the required users or devices.

To apply the configuration:

  • Create or edit the required policy.
  • Select the saved System Update Policy.
  • Assign the policy to the target users or devices.

VPN Configurations

VPN Configurations are used to define VPN connection settings that can be sent to managed devices through policies. These configurations help route device or managed application traffic through a company VPN connection.

This page supports two VPN configuration types: Custom SSL and Inhouse VPN. Custom SSL is used for custom VPN provider configurations, while Inhouse VPN is used for the company’s internal IKEv2-based VPN setup.

Policies » VPN Configurations opens the VPN Configurations page.

Configure VPN Configuration

To create a VPN configuration:

  • Click Add.
  • Select Custom SSL or Inhouse VPN.
  • Enter a clear Name for the configuration.
  • Fill in the required VPN connection values.
  • Select the Provider Type and VPN Type according to how the VPN should be used.
  • Configure iOS-specific settings if required.
  • Click Save.

Custom SSL

Custom SSL is used when the VPN connection is handled by a custom VPN provider or VPN application. In this mode, the admin defines values such as Remote Identifier, VPN Subtype, Provider Type, Authentication Method, Username and Password.

The Query Mappings option can be used in the Username field. For example, $username$ or $emailaddress$ can be replaced with the assigned user’s own information when the configuration is delivered.

Inhouse VPN

Inhouse VPN is used for the internal VPN configuration managed by the system. In this mode, the admin defines values such as Local Identifier, Server Address, Remote Identifier, Provider Type and VPN Type.

Inhouse VPN configurations also support additional management actions such as testing the VPN connection and managing user certificates.

Provider Type

Provider Type defines how the VPN provider handles traffic.

  • App Proxy is used when VPN traffic is handled at application level.
  • Packet Tunnel is used when the VPN handles packet-level network traffic.

VPN Type

VPN Type defines the scope of the VPN configuration.

  • All Apps applies the VPN configuration generally.
  • Only Specified Apps is used when VPN should be applied only to selected managed applications.

This is useful for per-app VPN scenarios where only corporate or managed apps should use the VPN connection.

iOS Specific Settings

The iOS-specific section allows the admin to define domain-based VPN behavior.

  • Safari Domains define Safari-related domains that should use the VPN behavior.
  • Associated Domains define app or service domains related to the VPN configuration.
  • Excluded Domains define domains that should not use the VPN.
  • Vendor Config is used to send provider-specific values such as Group, Realm, Role or Login Group / Domain.

These values should be configured according to the VPN provider or company VPN requirements.

Managing Existing VPN Configurations

Saved VPN configurations are listed on the page. Existing configurations can be managed with the following actions:

  • Clone: Creates a similar VPN configuration from an existing one.
  • Test: Opens the test area for the selected VPN configuration.
  • Manage: Opens certificate and user-related management options for Inhouse VPN configurations.
  • Delete: Removes the selected VPN configuration after confirmation.

Testing Inhouse VPN Configurations

For saved Inhouse VPN configurations, the Test action opens a test section under the selected VPN row. This area is used to check whether the VPN configuration and related network connection are working before or after the configuration is assigned to devices.

The test section may include options such as:

  • Server Connection
  • Single Host Ping
  • Multiple Host Ping
  • Telnet
  • DNS
  • CURL
  • Trace Route
  • IP Leases
  • Connected Clients

After selecting the required test type, click Test. The result is shown in the Results area. These tests help the admin verify VPN server availability, host reachability, DNS behavior, routing and connected client information.

Testing a VPN configuration does not send it to devices. It is only used to validate or troubleshoot the selected VPN configuration from the admin panel.

Sending VPN Configurations to Devices

Creating a VPN configuration does not apply it to devices automatically. After saving the configuration, it must be added to the related policy and assigned to the required users or devices.

To apply the configuration:

  • Create or edit the required policy.
  • Select the saved VPN Configuration.
  • Assign the policy to the target users or devices.
  • The VPN settings are sent to devices through the policies.

CHAPTER 10: COMMANDS

Command States

  • Not Sent: The command is created and stays in the server (DB)
  • At Push Server: The command is successfully transmitted to the Push Notification Server. (Google, APNS, etc.)
  • Push Server Error: Push Notification Server rejects the request to send the command
  • Transmitted: The command is delivered to the device, but its result has not been returned yet
  • Success: The device executed the command and returned success result.
  • Error: The device executed the command and returned error result
  • Malformed: The device decided that the command is malformed
  • Auto: state when command sent by devices automatically

Processes of Commands

Some MDM commands sent to Android, iOS and W8 devices includes data in it, processes of this kind of commands is explained below.

Firstly command is created and state of this command will be “Not Sent” when the command is in database at Server. Command is sent to Notification server of “Android, iOS or W8” devices. Notification Server returns a response about validity of the sent message. If the response is positive then state of command changes as “At Push Server”, or if the response is negative then state of command changes as “Push Server Error”. Later, command is sent to device and command is committed by device. After device committed the command, send message to server. This message is categorized in 3 different states, these are “Success, Error and Malformed”.

  • If the transaction is realized successfully, then state of the command will be changed as “Success” and message will be sent to server. Some commands includes data in itself, in such cases “command data” is send in message to server
  • If the transaction is not realized successfully, then state of the command will be changed as “Error” and message will be sent to server
  • If the transaction is not realized successfully as the command is wrong, applicable, missing or unknown then state of the command will be changed as “Malformed” and message will be sent to server

Processes of iOS Devices- MDM commands

Some MDM commands sent to iOS devices does not include data in it; therefore, device wants command from server itself. Processes of this kind of command is explained below.

Firstly command is created and state of this command will be “Not Sent” when the command is in database at Server. Command is sent to Notification server of “Android, iOS or W8” devices. Notification Server returns a response about validity of the sent message. If the response is positive then state of command changes as “At Push Server”, or if the response is negative then state of command changes as “Push Server Error”. Later, command is sent to device, information goes to device as it has a command. Device wants the command from server and state of the command is changed as “Transmitted”. Command is committed by device and the committed command message is send to server. This message is categorized in 3 different states, these are “Success, Error and Malformed”.

  • If the transaction is realized successfully, then state of the command will be changed as “Success” and message will be sent to server. Some commands includes data in itself, in such cases “command data” is send in message to server
  • If the transaction is not realized successfully, then state of the command will be changed as “Error” and message will be sent to server
  • If the transaction is not realized successfully as the command is wrong, applicable, missing or unknown then state of the command will be changed as “Malformed” and message will be sent to server
